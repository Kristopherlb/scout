# Scout Executable Public Walkthrough

## Problem

A public framework can look complete while its example uses invented scores,
stale evidence, or undocumented setup that a new operator cannot reproduce.

## Requirements

- [REQ-001] The public walkthrough MUST execute the real contract, bundle, development scorer, calibration, audit, refusal, and activation paths in isolation.
- [REQ-002] The public target bundle MUST exclude private holdouts, scorers, canaries, logs, audit evidence, and hub-side skills.
- [REQ-003] Public Pages, README, architecture, onboarding, SECURITY, and CONTRIBUTING documentation MUST identify the implemented walkthrough, request protocol, activation gates, and agent interface without unsupported capability claims.
- [REQ-004] CI MUST keep the walkthrough, public-release boundary, standards, sandbox isolation, quality checks, and secret scan blocking.

## Success Metrics

A stranger can run one command from a trusted clone, observe the incomplete
judgment refusal and successful finalized activation, and inspect which real
artifacts established each stage. The command leaves the caller's checkout
unchanged and uses no private evaluation material.

## Risks

A synthetic fixture can be mistaken for performance evidence. The walkthrough
labels its two-case range as demonstration-only and makes no population-level
claim. Its explicit non-container mode is limited to committed fixture code;
active operational polling still requires Docker.

## Assumptions

The walkthrough verifies framework mechanics, not a hosted service, external
GitHub integration, or the scientific quality of an operator's future target.
