THE 30-SECOND VERSION

Think driving lessons, not a worksheet.

A

The goal

You want a driver who can handle unfamiliar roads—not someone who memorized one route. LFD turns “be good at this task” into a score that rewards transferable skill.

B

The trick

Let the agent practice on examples it can see, but test it on cases it cannot access. Reveal only enough feedback to steer—not enough to reconstruct the exam.

C

The proof

If practice and hidden scores rise together—and the solution survives mutations—you have evidence of real capability, not clever answer memorization.

HOW IT ACTUALLY WORKS

A score becomes useful only when the experiment around it is honest.

IMPORTANT DISTINCTION

This is usually not neural-network training. There may be no gradient or backpropagation. The optimizer proposes software changes; the loss gives it a direction; the next cycle tests another hypothesis.

THE LOSS, SPECIFICALLY

Scout does not impose one universal formula.

Each target gets a mechanical scorer suited to the outcome: precision and recall for retrieval, structured output comparison for APIs, pixel difference for visual work, or another task-matched metric. Scout standardizes the contract around that scorer.

L(candidate)=1 − Score(candidate on cases)

Lower loss is better. Acceptance is measured on the blinded holdout—not the visible development set.

ALGORITHM 01N

Size the exam before the run

Start with the target score p, the smallest meaningful difference δ, and a confidence level whose critical value is z.

N = ⌈z² · p(1 − p) / δ²⌉

At p = .80, δ = .05, and 95% confidence: N = 246 cases.

ALGORITHM 02CI

Put uncertainty around the score

Resample the case-level results with replacement, recompute the score many times, and take the outer percentiles as the interval.

CI₉₅ = percentile(bootstrap(scores), 2.5, 97.5)

A score of .74 with [.71, .77] says what the data can actually support.

ALGORITHM 03Δ

Detect reward over-optimization

Over the configured recent window, compare the development lower bound with the hidden score. Scout allows a 2% tolerance before calling the holdout flat.

dev_low[end] > dev_low[start]
holdout[end] ≤ 1.02 × holdout[start]

If both are true, flag divergence and redesign the loss.

ALGORITHM 04ℹ

Budget the information leak

Estimate how many bits each response reveals, multiply by expected cycles, and compare that with the information needed to identify the evaluation items.

fraction ≈ (bits/call × cycles)
÷ (log₂(N) × N)

Above the threshold, reduce feedback detail or grow the eval.

THE RUNTIME ALGORITHM

What poll-and-score does.

The private hub processes unseen request tags oldest-first. Every agent-supplied value is parsed as a validated number, enum, or null—never interpolated into executable code.

  • Inactive, over-budget, duplicate, or rate-limited requests do not run.
  • A failed liveness check receives a truthful score of zero.
  • Sandbox failure aborts without inventing a score.
  • One validated row is appended for every completed scoring cycle.
for tag in unseen_tags(oldest_first):
  enforce(rate_limit, run_budget)
  sha = resolve_pinned_commit(tag)

  if not sandboxed_liveness(sha):
    result = Score(0, [0, 0])
  else:
    outputs = sandbox_generate(sha,
      network=OFF, source=READ_ONLY)
    result = trusted_compare(outputs, holdout)
    probe  = maybe_run_mutations(outputs)

  append_once(log, result, probe, harness_hash)
  flags = check_divergence(log) + check_probes(log)
  post_status(result.score, result.interval, flags)
IN OTHER WORDS

The loss says which way to move. The holdout asks whether the move generalizes. The interval asks whether the change is real. The probes ask whether it is brittle. The security boundary asks whether the evidence can still be trusted.

ONE OPTIMIZATION CYCLE

From hypothesis to honest signal.

Each cycle changes one thing, measures it twice, and records the result. That discipline is what turns a string of edits into an experiment you can learn from.

  1. 01

    PREREGISTER

    Write the hypothesis

    Predict the change, the expected lift, and the likely failure mode before editing.

  2. 02

    BUILD

    Change one variable

    Keep the edit narrow enough that a score movement has a plausible cause.

  3. 03

    INNER LOOP

    Run visible tests

    Fast development cases catch obvious failures and guide everyday iteration.

  4. 04

    REQUEST

    Tag a pinned commit

    An immutable holdout-check-v1-<sha12>-<request-id> tag binds the request to one exact commit.

  5. 05

    OUTER LOOP

    Score in isolation

    Target code generates outputs in a sandbox; comparison happens outside it.

  6. 06

    DECIDE

    Read the trend, not a blip

    The agent receives a bounded status. The hub retains the detailed audit trail.

THE SCIENCE, MINUS THE HEADACHE

The score is a compass—not the destination.

A loss function is simply a repeatable way to say “warmer” or “colder.” The danger is that a tireless optimizer will find shortcuts in the measurement. LFD wraps the score in checks that make genuine improvement the easiest remaining path.

01 Power analysis “How many test cases are enough?” +

Before a run starts, LFD chooses the smallest improvement worth detecting and the confidence required. A calculation then sets the minimum number of cases. For example, distinguishing a five-point change around an 80% target at 95% confidence needs roughly 246 cases—not a guess, and not “whatever we had.”

Plain English: a tiny exam can make luck look like progress.
02 Bootstrap confidence intervals “How sure are we about the score?” +

A score such as 0.74 is only an estimate from one set of cases. LFD repeatedly resamples case results—typically 1,000 times—to estimate a plausible range, such as 0.71–0.77. The loop reacts to meaningful movement in that range, not every noisy decimal wiggle.

Plain English: report “74%, give or take,” not false precision.
03 Mutation testing “Does the skill survive a remix?” +

Inputs are systematically changed—paraphrased, reordered, shifted to a boundary, or given a new entity—while preserving the underlying task. Scores are reported by operator, so a result can reveal that paraphrases work while entity swaps fail.

Plain English: memorization breaks when the question changes clothes.
04 Goodhart’s Law “When a measure becomes a target…” +

Aggressive optimization exposes every gap between a metric and the outcome it was meant to represent. LFD classifies the likely shortcuts, then matches each with the right kind of defense.

  • RegressionalChasing noise in the test
  • ExtremalPushing a useful knob past its useful range
  • CausalChanging the measuring machinery itself
  • AdversarialActively hunting gaps in the metric
05 Dev / holdout divergence “Are we learning—or gaming?” +

Scout watches recent score intervals. If the visible development score keeps climbing while the hidden holdout score stays flat or falls, that is the classic reward-over-optimization signature. The run stops treating the metric as safe and triggers a redesign of the loss function.

Plain English: better homework, same final exam = investigate.

DEFENSE IN DEPTH

Every shortcut leaves a footprint.

No single check is perfect. Scout combines independent signals so that hiding from one detector tends to make a different detector light up.

CNY

Canaries

Unique strings embedded in hidden answers turn any later appearance into proof of access.

N·G

Overlap lint

Phrase-level similarity catches near-verbatim leakage that exact canaries can miss.

ZIP

Compressibility

Solution size growing with the eval can reveal a disguised lookup table.

COV

Coverage variance

Identical code paths across cases suggest dispatching answers instead of doing the work.

LIV

Liveness

The product must actually build, boot, and answer before any evaluation is scored.

CAL

Calibration

The scorer must clearly separate a known-good result from a known-bad one.

COMMON QUESTIONS

Short answers for sensible skeptics.

Is LFD just “more testing”?

No. Conventional tests mainly check known requirements. LFD adds a sparse outer loop designed for repeated optimization: blinded cases, measured uncertainty, information limits, anti-cheat signals, and explicit stop conditions.

Why not show the agent every failure?

Because case-level feedback leaks information. Across enough cycles, a capable agent can reconstruct the hidden set. Aggregate feedback preserves direction while reducing that reconstruction channel.

Does a high score prove the system is safe?

No. It is evidence about the task distribution represented by the eval, not universal proof. Confidence intervals quantify sampling uncertainty; audits and probes look for failure modes the headline score may hide.

What happens when the agent finds a shortcut?

Patch the loss function, not the agent. The design process classifies the exploit, adds a matching fence and detector, rotates exposed cases, recalibrates, and only then resumes optimization.

Why one variable per cycle?

If five unrelated changes land together, a better score cannot tell you which idea worked. Narrow cycles preserve causal learning and make reversals much safer.

What does Scout publish?

The public repository contains the reusable framework and synthetic examples only. Real holdouts, canaries, target configuration, and score histories belong in a separate private operational repository.

THE WHOLE IDEA IN ONE LINE

Build fast feedback for learning—and a separate truth for knowing.

Scout makes it possible to optimize aggressively while keeping the evidence honest, auditable, and difficult to game.
